7.3.3 并发查询（C 组）

20 个并发会话各连续发起 5 次订阅模糊查询（共 100 次请求），全部成功（成功率 100%），总耗时 0.44 s，吞吐约 229.6 req/s，无错误响应，说明应用层按角色划分的连接池在并发场景下工作稳定。

7.3.4 并发下单与死锁问题修复（D 组）

10 个线程同时调用存储过程 sp_place_order 提交订阅单。初版取号实现采用 SELECT ... FOR UPDATE 锁定最近订单行，该场景下触发 MySQL 死锁（ERROR 1213）：多个事务同时以降序对主码索引加next-key锁后插入，形成插入意向锁冲突。定位后改用命名锁 GET_LOCK('press_order_no', 10) 对"取号"临界区串行化（见 5.3 节存储过程代码），重新测试结果如下：

表 7-8 并发下单取号唯一性验证（修复后）
测试项结果
并发线程数10
成功生成订阅单10 张（无失败、无死锁）
订单号唯一性10/10 全部唯一（SO0000116 ~ SO0000125 区间内连续分配）

修复后并发下单无死锁、无重复取号，验证了事务设计与命名锁方案的正确性。该问题由性能测试发现并闭环解决，体现了"测试驱动改进"的过程。

结论：在当前数据规模（每表 50~450 行）与本机环境下，系统各页面平均响应时间低于 30 ms，典型 SQL 均值低于 2 ms，20 并发查询成功率 100%，并发下单取号严格唯一，数据库访问功能与性能均满足课程设计要求。
